# 元件化撰寫與靜態審閱

[English](../../skills/svg-ui-bridge/references/component-authoring.md)

當重複的元件、多個畫面變體或狀態比較，讓手寫 SVG 或 HTML 變得難以維護時，請閱讀這份文件。工具讀的是 SVG（HTML 路線則是 HTML），但那不一定是你手寫的格式。

## 選擇最小夠用的撰寫方式

- 小型的現有 SVG 或 HTML 草稿，抽成元件的工作量比省下的還多時，就直接編輯。不要只為了一份小草稿引入建置流程。
- 重複的卡片、列、控制項或畫面變體，優先用 TSX 函式和有型別的 props。專案有設計建置流程就沿用。這裡的 JSX 是建置時用的範本語言，不需要 React 應用程式、hydration、事件處理或開發伺服器。
- 共用的顏色、字型和尺寸集中在一個主題模組；重複的內容用資料陣列。每個元件實例都明確傳入穩定的 id。輸出要保留 SVG 規範，包括 `data-component`、`data-layout`、token、目標尺寸和狀態圖層。
- SVG 的 `defs`/`use` 不能取代有型別的元件組合。UI 元件要輸出成可檢視的 `<g>` 實例，元件清單和 Quick Edit 才能分辨每個實例。
- 要執行真正的型別檢查，例如 `tsc --noEmit`。建置成功只代表程式碼能轉譯，不代表型別正確。

建議的專案結構（依現有路徑調整）：

```text
design/system/components/    共用的 TSX 設計元件
design/system/theme.ts       共用的設計 token
design/system/pages/         畫面範本與明確的變體
design/system/build.tsx      靜態匯出的進入點
design/*.svg                產生的工具輸入與審閱檔案
```

svg-ui-bridge 的 repo 在 `examples/tsx-design/` 有一個可執行的範例：用共用的 Button 元件產生同一畫面的兩個靜態狀態，附鎖定版本的相依套件、lockfile 和 `typecheck` 腳本。它不屬於安裝後的 skill。使用時把資料夾複製到 `design/system`，在那裡執行一次 `npm ci`，再執行 `npm run typecheck` 和 `npm run build`。只有撰寫時需要 Node.js 和 npm，Python 工具不需要它們。範例沒有自動監看：每次修改來源後，都要先重新建置，再預覽、檢查、產生元件清單或匯出 token。

## 只有一個可編輯的來源，輸出可重現

在專案說明中記錄來源路徑和建置指令。修改 TSX、主題或資料後重新建置；不要把直接修改產生的 SVG 當成長期修改。Quick Edit 仍然指向 `file.svg#ComponentId`：先重現它的 snapshot，再依穩定 id 找回來源。共用元件改變時，重新產生並檢查所有用到它的畫面。

提交來源、建置設定和 lockfile。預設也提交產生的 SVG 和元件清單，作為可審閱的快照。若專案的建置或 CI 會在審閱與驗證前重新產生，也可以忽略產生的檔案，但要記錄這個做法。手寫的 SVG 絕不能忽略。可編輯的來源是你修改的對象；核准的產生 SVG 是視覺基準。重新產生後若改變了已核准的輸出，要先審閱才能成為新基準。設計元件要和產品程式碼分開，在目標技術棧中實作核准的外觀和行為。

## 比較畫面，不比較互動

選出和決策有關的狀態（例如 default、empty、loading 或 error），各自輸出成同尺寸、有名稱的檔案，預覽頁就會同時顯示。各檔案的 id 保持一致。`data-state` 圖層和預覽頁的狀態切換仍適合檢查單一元件；`svg_render.py --all-states` 可輸出它們的快照。不要讓審閱者得點過一個能運作的應用程式才看得到各種方案。

相關的畫面放在同一個標題下，畫面外附簡短理由。對齊要比較的畫布，讓說明文字可換行，並和真正的 UI 文案區分開。只比較足以解決當前問題的方案數量。記錄核准的是哪個檔案、狀態和尺寸，實作時沿用同一個基準。

預覽頁的縮放、選取和 Quick Edit 是審閱工具，不是產品行為。不要在設計草稿裡加入應用程式邏輯。

## 讓上下文保持精簡

讀取和修改來源元件、它的 props 和主題，而不是反覆載入展開後的輸出。實作時只交接元件清單的那一列和單獨算出的圖。產生的檔案很大，不代表 token 用量一定高；請分開檢查來源的重複程度和過大的幾何資料。沒有實測前，不要承諾 token 節省比例。
